# BabelCodex v0.1.0

## Release summary

BabelCodex v0.1.0 is the first public development release of a local-first PDF
translation workbench built around BabelDOC and the official Codex SDK. This
release provides the current Windows x64 GUI executable build produced by the
repository's GitHub Actions workflow.

The project is intended for personal, local use. It is not a hosted translation
service, a multi-tenant SaaS product, or a replacement OpenAI-compatible API.

## Included assets

- `BabelCodex-v0.1.0-windows-x64.exe` — the Windows x64 Tauri GUI executable.
- `BabelCodex-v0.1.0-windows-x64.7z` — a 7z archive containing exactly that
  one GUI executable and no installer files, sidecar files, configuration,
  logs, state, cache, user PDFs, or credentials.

The archive is checked in CI by extracting it into a temporary directory and
requiring exactly one file with the expected executable name.

## Implemented capabilities

- BabelDOC 0.6.x compatibility boundary with the observed 0.6.4 runtime.
- Official `openai-codex` SDK adapter using the user's Codex/ChatGPT sign-in
  path; no cookie extraction, undocumented ChatGPT HTTP endpoint, or silent API
  key fallback.
- Single-pass PDF orchestration through a worker process.
- Structured JSONL sidecar protocol shared by GUI, CLI and MCP application
  service paths.
- Placeholder preservation and output validation for rich-text/formula tokens,
  URLs, citations and related protected content.
- Bounded validation retry behavior with explicit error categories.
- Persistent job state, artifact manifest validation, explicit retry, output QA,
  conservative worker-crash recovery and scoped cleanup.
- YAML-only portable configuration with paths rooted at the application
  directory for portable Windows layouts.
- Settings, logging, credential-like value redaction, restricted PDF staging and
  first-use output-directory confirmation.
- Translation Gateway batching boundary, SQLite translation cache, glossary and
  document-context support, and a deterministic mock-only batching benchmark.
- Local stdio MCP operations with scoped job/path behavior and no arbitrary shell
  execution or unrestricted file deletion.
- Tauri 2 + React/TypeScript GUI with source-level tests and build validation.

## Windows validation boundary

Successful GitHub Actions construction proves that the source can be built in
the hosted Windows environment. It does **not** by itself prove complete native
Windows acceptance. The following remain separate validation items and are not
represented as release PASS merely because assets were built:

- first-use output confirmation on a fresh Windows profile;
- native file picker, Unicode/space/drive-letter paths and path permissions;
- cancellation, reconnection, stale-sidecar presentation and window lifecycle;
- DPI at 125%, 150% and 200%, keyboard navigation and NVDA;
- clean-user install/upgrade/uninstall behavior;
- Defender/SmartScreen behavior, signing, SBOM and release-security audit;
- MSI/NSIS installer parity where applicable;
- authorized live Codex authentication, real PDFs and long-document acceptance.

The authoritative current matrix and any blocked/not-run reasons remain in
`docs/validation/windows.md`. The overall Windows state remains
`WINDOWS_VERIFICATION_PENDING` until those platform-specific checks are
executed and recorded.

## Installation and first run

This release asset is an executable-focused development release, not a signed
installer. Place the executable in a writable directory and follow the current
project configuration and authentication instructions in `README.md`. A real
Codex/ChatGPT sign-in is required for live translation; ordinary tests and the
release build do not perform a live Codex request.

Do not place user PDFs, logs, state, cache, credentials or private glossary data
inside the public repository or release archive.

## Known limitations

- The 7z archive intentionally contains only the GUI executable because that is
  the requested asset shape; it is not a complete portable directory bundle.
- The GUI executable is unsigned development software and may trigger Windows
  SmartScreen warnings.
- The bundled sidecar/runtime and first-launch resource behavior must still be
  validated on a target Windows machine according to the Windows handoff.
- Browser-mode WDIO and some native desktop checks may remain environment
  blocked even when source tests and the hosted build pass.
